# ジョブの識別と注釈の引き継ぎ

## 識別する対象

cron の実行行と、その行が表す定義を分ける。

- `definition_id`：タグ・表示名を関連付ける定義の ID。同一の取得元・実行環境・cron 式・コマンドを共有する行は同じ値になる。
- `id`：収集結果の各行を区別する ID。`definition_id` に同一定義の出現連番（1始まり）を付ける。コマンド取得 API とタイムラインの `task_id` にはこちらを使う。
- `duplicate_count`：今回収集できた範囲にある同一定義の行数。

同じ定義が複数あってもタスクと実行予定を統合しない。タグ・表示名は `definition_id` 単位で共有する。実行時刻や末尾コメントが異なる行は共有しない。同じ行を区別する根拠がないため、出現連番を注釈の保存キーにしてはいけない。重複行の増減後に「以前の何行目が残ったか」は判定しない。

## 変更ごとの扱い

| 変更 | 定義 ID と注釈の扱い |
| --- | --- |
| ジョブ行の並べ替え・別の行の挿入・行番号の変更 | 維持。ただし環境変数の宣言境界を越える移動は別定義 |
| 空行・独立した `#` コメント行の追加・削除 | 維持 |
| 標準 cron 行の先頭インデント・5フィールド間・コマンド直前のスペース／タブ | 維持 |
| 改行コード LF / CRLF | 維持 |
| 時刻・曜日等のフィールド文字列の変更 | 別定義。`0` と `00`、曜日名の大小文字等も同値推測をしない |
| 実行ファイル・引数・引用符・コマンド内部／末尾の空白・リダイレクト・シェル構文の変更 | 別定義 |
| コマンド末尾の `#` コメント・QTS の識別コメントの変更 | 別定義。引用符内の `#` 等との区別やシェル解析をしない |
| 設定タイムゾーン・取得元・環境変数宣言の変更 | 別定義 |
| 完全に同じ定義の行の増減 | 定義 ID を維持。表示行数・出現連番・duplicate_count は収集結果に合わせる |
| 消えた定義と完全に同じ定義の再登場 | 同じ定義 ID。保存済みの注釈を再利用する |
| 未対応・分離不能行の変更 | 行の原文が一致する場合だけ維持。インデント等も正規化しない |

コマンドにはシェルにとって意味を持つ空白やコメントがある。コマンド名の類似、同じ時刻、行位置、1件だけの差分等を根拠に別定義を同じジョブとして扱わない。解析エラーの解消や `@reboot` 等への対応により識別方法が変わる場合も、自動で注釈を移さない。

## ID の計算

UTF-8 の JSON 配列を `ensure_ascii=False`、区切りを `(',', ':')` として直列化し、SHA-256 の64桁の16進表記を使う。取得日時・行番号・mount 先のパス・次回予定は計算に含めない。論理取得元は `/etc/config/crontab`、タイムゾーンは設定された `QSV_TIMEZONE` の文字列。

1. 環境変数の宣言をファイル順に集める。変数名と `=` の前の空白だけを除き、`NAME=value` として値・宣言順・重複宣言を保持する。設定値は公開しない。
2. `['cron-context-v1', 取得元, タイムゾーン, 宣言配列]` のハッシュを収集単位で計算する。
3. 行より前にある環境変数宣言の数を `scope` とする。
4. 標準の5フィールドとコマンドを分離できる行は、`['standard', フィールド配列, コマンド原文]` を定義とする。分離不能・未対応行は `['opaque', 行原文]` とする。時刻値が範囲外でも5フィールドを識別できれば前者。
5. `['cron-v1', contextのハッシュ, scope, 定義]` をハッシュ化し、`cron-v1-` を付けて `definition_id` とする。

環境変数は QTS の適用範囲・展開を推測せず、ファイル全体の宣言列と行の宣言境界の両方を識別条件にする。後方の宣言を変更した場合も、そのファイルの全定義が変わる。無関係と断定して注釈を付け替えることを避けるため、環境変数変更時の継続性は保守的に扱う。

環境変数やコマンドの原文は ID に埋め込まない。通常 API には ID・重複数だけを追加し、原文の取得は引き続き個別の表示操作時に限る。ハッシュ化は暗号化や秘密情報を隠す保証ではなく、閲覧権限は既存のアクセス制御に従う。

バージョン付きの計算規則を固定し、将来規則を変える場合は別バージョンの ID と明示的な移行を用意する。形式が違う ID 間の類似度照合は行わない。DB は QSV インスタンス単位とし、複数 NAS 間で注釈 DB を共用しない。

## 注釈の保持と明示的な引き継ぎ

注釈は QNAP ローカルの SQLite に保存し、詳細画面と「タグ・表示名」画面から編集・明示コピーする。収集結果とコマンドはメモリにのみ保持する。API・保存・バックアップの詳細は [annotations.md](annotations.md) を参照。

- タグ・表示名は `definition_id` をキーに保存する。収集時に注釈のキーを付け替えない。
- 定義が見えなくなっても注釈は自動削除せず、利用者が削除するまで保持する。同じ定義が再登場すれば共有注釈を再利用する。
- 完全取得（`ok` / `empty`）の結果だけで不在を判定する。`partial`・取得失敗・タイムアウト・古いキャッシュでは不在と断定しない。500件上限時の重複数は収集範囲の値であり、実機の全件数ではない。
- 時刻・コマンド等の変更後の定義に注釈を引き継ぐ場合、利用者が移行元・移行先の定義を明示選択し、影響する重複行の範囲を確認して注釈をコピーする。移行元は残す。置換・競合の処理も明示する。
- 同時編集や再取得に備え、移行先が現在存在することと注釈の版を更新時に再検証する。QTS の crontab に識別子を書き込まない。

これにより、再収集やコンテナ再起動で同じ定義の注釈を参照でき、変更された別定義にタグ・表示名が自動で移ることを防ぐ。別の目的で完全に同じ定義を再作成した場合は区別できないため、注釈の明示削除・変更で対応する。
