# QNAP QTS Schedule Viewer 開発依頼・仕様書

## 1. プロジェクト概要

### 1.1 目的

QNAP QTSでは、cron、電源管理、ストレージ管理、バックアップ、各QPKGアプリケーションなど、さまざまな場所にスケジュール設定が分散している。

これらを横断的に収集し、**NAS全体の定期実行タスクを単一のWeb画面で可視化するツール**を開発したい。

主な目的は次のとおり。

- NAS全体で何の処理がいつ実行されるか把握する
- 特定の曜日・時間帯にタスクが集中していないか確認する
- メンテナンス、バックアップ、スキャンなどのスケジュール重複を発見する
- 設定変更が必要な場合に、QTSのどの管理画面で変更すべきか確認する

**本ツールは読み取り専用とする。スケジュールの追加・変更・削除・有効化・無効化は実装しない。**

### 1.2 利用環境

- NAS：QNAP
- OS：QTS（QuTS heroは当面対象外）
- コンテナ実行環境：QNAP Container Station / Docker（収集・API・Web UI）
- Tailnet 公開ホスト：server-a（QSV 専用 Tailscale コンテナと Caddy）
- QNAP 上では Tailscale は動かさない
- 公開範囲：Tailscale Tailnet内のみ
- 利用端末：PC、スマートフォンのWebブラウザ
- 利用者：NAS管理者
- タイムゾーン：NASに設定されたタイムゾーン（通常 Asia/Tokyo）

QTSの具体的なバージョン、CPUアーキテクチャ、各QPKGのバージョンは実機調査で確認する。

### 1.3 基本方針

1. シンプルで軽量なWebアプリケーションとする。
2. ホストOSやQNAP標準機能には変更を加えない。
3. 原則としてローカルの設定情報を読み取り、外部クラウドサービスに依存しない。
4. Docker Composeで構成を管理できるようにする。
5. スケジュール収集処理と画面表示処理を分離する。
6. QTSのバージョン差やQPKGの有無に対応できる拡張可能な構造にする。
7. Tailnet内への公開は、server-a 上の QSV 専用 Tailscale コンテナと Caddy を利用し、LAN 経由で QNAP 上のアプリへ転送する。

## 2. 画面仕様

### 2.1 メイン画面

最も重要な画面は、全スケジュールを横断的に表示する週間タイムラインである。

#### 週間タイムライン

- 横軸：曜日（月曜〜日曜）
- 縦軸：時刻（0:00〜24:00）
- 各タスクの実行予定時刻にマーカーを表示
- スケジュールの分類ごとに色分け
- マーカーを選択すると詳細情報を表示
- 同一時刻に複数のタスクがある場合は重なりが分かる表示にする
- 前週・次週・今週への移動
- 日付を指定した表示
- 直近7日間と暦週（月曜始まり）の切り替え

実行時間が不明なタスクは、開始時刻のみを表示する。

終了時刻や所要時間を取得できる場合に限り、時間帯を帯状に表示する。取得できない場合は、推測した実行時間を表示しない。

#### 高頻度タスクのフィルタと月間カレンダー

- 実行頻度で「高頻度を除外」「すべて」「高頻度のみ」を選択できる
- 高頻度は実行対象日の通常24時間で24回以上とし、cron の分・時フィールドから計算する
- 初期表示は高頻度を除外し、非表示件数を表示する。算出不可の設定は除外せず残す
- 一覧・週間・月間・CSV で同じ頻度フィルタを使う
- 月間カレンダーは月曜始まりとし、前月・次月・今月・指定月へ移動できる
- 日ごと・タスクごとに最初の予定時刻と回数を表示する
- 日付から週間表示へ、タスクから詳細へ移動できる
- 毎分タスクの月間予定は全イベントを展開せず集約する

#### カテゴリ分類

初期分類として次を想定する。

| カテゴリ | 主な対象 |
|---|---|
| システム | QTS内部処理、cron |
| 電源 | 起動、シャットダウン、再起動 |
| ストレージ | RAIDスクラビング、S.M.A.R.T.、不良ブロックスキャン |
| スナップショット | 定期スナップショット |
| バックアップ | HBS 3、バックアップ、同期 |
| セキュリティ | ウイルススキャン、マルウェアスキャン |
| 更新 | ファームウェア・アプリケーション更新 |
| アプリケーション | QPKG固有のスケジュール |
| その他 | 分類できないジョブ |

カテゴリ色は固定し、フィルタリングできるようにする。

### 2.2 スケジュール一覧画面

表形式で全スケジュールを表示する。

表示項目：

| 項目 | 内容 |
|---|---|
| 名前 | 人間が理解できるタスク名 |
| カテゴリ | システム、バックアップなど |
| 提供元 | QTS、HBS 3、QPKG名など |
| 有効状態 | 有効、無効、不明 |
| 実行条件 | cron式、毎日、毎週など |
| 次回実行予定 | 算出できる場合のみ表示 |
| 設定場所 | QTS上の設定画面 |
| 取得元 | 参照した設定ファイルやAPI |
| 取得状態 | 正常、部分取得、取得不可など |

機能：

- 全文検索
- カテゴリによる絞り込み
- 提供元による絞り込み
- 有効・無効による絞り込み
- 実行時刻順ソート
- CSVエクスポート
- 必要であればJSONエクスポート

### 2.3 詳細画面

各スケジュールの詳細として以下を表示する。

- タスク名
- 概要
- カテゴリ
- 提供元アプリケーション
- スケジュール設定
- 次回実行予定（算出可能な場合）
- 有効・無効
- 設定元のファイルまたはAPI
- 元の設定値（安全に公開できる項目のみ）
- QTSでの設定変更場所
- 取得・解析時の注意事項

cronについては、実行コマンドを確認できるようにする。ただし、コマンドラインに資格情報やトークンなどが含まれる可能性があるため、機密情報はマスクする。

設定変更画面へのリンクが安全かつ確実に構成できる場合は提供してよい。そうでなければ、メニュー階層を文字列で表示する。

### 2.4 収集状況画面

**スケジュールが存在しないことと、取得できなかったことを明確に区別する。**

収集対象ごとに、以下を表示する。

- 対応済み
- 対応済み・該当タスクなし
- 部分的に取得
- 未対応
- アプリ未インストール
- アクセス権限不足
- 解析エラー

最終収集日時、前回収集結果、エラーの概要を確認できるようにする。

この画面があることで、可視化結果がどの程度網羅的なのかを管理者が判断できるようにする。

## 3. スケジュール収集仕様

### 3.1 設計方針

スケジュールごとに独立したCollectorを実装する。

例：

- `CronCollector`
- `PowerScheduleCollector`
- `StorageScheduleCollector`
- `SnapshotCollector`
- `HbsCollector`
- `SecurityScheduleCollector`
- `QpkgCollector`

各Collectorは、取得した情報を共通のデータ形式に変換して返す。

取得元ごとの差異をバックエンドで吸収し、フロントエンドが設定ファイルの構造に依存しないようにする。

### 3.2 収集対象の優先順位

#### P0：最優先

- QTSのcron設定
- 電源スケジュール
- RAIDスクラビング
- S.M.A.R.T.テスト
- スナップショット
- HBS 3のバックアップ・同期ジョブ

#### P1：次の優先度

- ファームウェア更新
- Malware Remover
- Antivirus
- その他QTS標準のスケジュール設定

#### P2：拡張対象

- その他のQPKGアプリケーション
- 個別アプリケーション固有のスケジュール
- Container Station内のユーザー定義ジョブ

P0については、まず実機でどのように設定が保存されているかを調査する。

取得できない対象がある場合、推測による実装は行わず、理由と代替案を報告する。

### 3.3 cron

既知の取得元：

`/etc/config/crontab`

QNAP固有の永続化設定であることを考慮する。

要件：

- cron式を解析する
- コメント行を除外する
- 標準的な5フィールドのcron式に対応する
- QTSで確認された独自記法があれば必要に応じて対応する
- 不正または未対応の式はエラーとして表示する
- ジョブの次回実行予定を算出する
- 人間が理解できる説明に変換する
- 既知のQTS内部コマンドは分かりやすい名称に変換する
- 元のcron式を保持する

例：

`0 3 * * 0` → 毎週日曜日 03:00

cron式に基づく予定実行時刻と、実際の実行履歴は区別する。

cronの曜日・月末判定などは標準的なcronの挙動に従う。DSTやタイムゾーン変更も考慮する。

### 3.4 cron以外のQTS内部スケジュール

QTSの各機能で使用される設定ファイル、データベース、内部APIなどを調査し、読み取り専用で取得する。

特に、以下を調査対象とする。

- 電源管理のスケジュール
- ストレージのメンテナンススケジュール
- スナップショットのスケジュール
- HBS 3のジョブスケジュール
- セキュリティスキャンのスケジュール

取得方法は次の優先順位で検討する。

1. 公式に公開・文書化された読み取りAPI
2. 安定した設定ファイルやデータベースへの読み取りアクセス
3. 読み取り専用で利用できるQTS内部インターフェース

未公開APIや内部DBにアクセスする場合は、QTSアップデートにより破損する可能性があるため、Collector単位で障害を隔離する。

取得元が設定内容ではなく実行履歴しか提供しない場合は、設定スケジュールとして扱わない。

### 3.5 重複排除

同じジョブが複数の取得元に存在する可能性を考慮する。

例えば、QTS管理画面から設定されたジョブが、内部的にはcronとして登録されている場合である。

このような場合、同じジョブを二重表示しないことが望ましい。

ただし、コマンド名や実行時刻が一致するだけで同一ジョブと断定しない。

根拠がある場合のみ統合し、元の取得元情報は保持する。判断できない場合は別々に表示する。

## 4. データモデル

最低限、次のような論理構造を定義する。

```json
{
  "id": "stable-identifier",
  "name": "RAID Scrubbing",
  "description": "RAID整合性チェック",
  "category": "storage",
  "provider": "QTS",
  "enabled": true,
  "schedule": {
    "type": "cron",
    "expression": "0 3 1 * *",
    "timezone": "Asia/Tokyo"
  },
  "next_runs": [
    "2026-11-01T03:00:00+09:00"
  ],
  "duration_seconds": null,
  "source": {
    "collector": "storage",
    "type": "config",
    "location": "verified-source"
  },
  "configuration_location": "ストレージ＆スナップショット",
  "collection_status": "ok"
}
```

上記はデータ構造の例であり、実際のRAIDスクラビングの取得元や設定形式を意味しない。

設計上の要件：

- `enabled` は true / false / null を許容する
- スケジュールにはcron以外の形式も使用できるようにする
- 毎月最終日、隔週、特定曜日、単発実行などを表現できるようにする
- タイムゾーンを明示する
- 時刻を計算できないものは、無理に計算しない
- 次回実行予定と実行履歴を混同しない
- 安定したIDで同一ジョブを識別する

## 5. システム構成

### 5.1 推奨構成

シンプルな単一コンテナを第一候補とする。

推奨技術：

- Python 3
- FastAPI
- Jinja2および軽量なJavaScript
- croniter等のスケジュール解析ライブラリ
- Docker / Docker Compose

React等の大規模SPAフレームワークは必須としない。

ただし、週間タイムラインの実装に明確な利点がある場合は、軽量なUIライブラリを採用してよい。

実行時にNode.jsの常駐プロセスなどを追加する必要はない。

### 5.2 コンテナ構成

概念的には次の構造とする。

```text
QNAP QTS Host
│
├── QTS Settings
│   ├── crontab
│   ├── Power schedule
│   ├── Storage settings
│   ├── Snapshots
│   └── QPKG settings
│
├── Read-only collection interface
│
└── Docker / Container Station
    │
    └── qts-schedule-viewer
        ├── Collectors
        ├── Normalization
        ├── Schedule calculator
        ├── REST API
        └── Web UI
               │
               └── 制限された LAN バックエンド入口
                         │
                  server-a
                    ├── リバースプロキシ / HTTPS 終端
                    └── QSV 専用 Tailscale コンテナ
                              │
                            Tailnet
```

ホスト上の設定情報を収集するために、読み取り専用のbind mountなどを利用する。収集・キャッシュ・API・Web UI は QNAP 上の単一アプリに置き、server-a はリバースプロキシだけを担当する。両者は別ホストであり、Docker bridge network の共有は前提としない。

ただし、実装方式はセキュリティ上の影響を検討したうえで決定する。

### 5.3 ホスト情報へのアクセス

最優先事項は、**QTSホストに対して変更を加えないこと**である。

要件：

- 原則としてファイルシステムを読み取り専用でマウント
- Docker privilegedモードは使用しない
- Docker socketはマウントしない
- 必要最小限のディレクトリ・ファイルのみ共有
- ホストの設定ファイルに書き込みを行わない
- QTSの管理APIを使用する場合もGET相当の参照操作のみ
- 機密情報や認証情報を収集・表示しない

QTSの管理設定には、スケジュールとは無関係の機密情報が含まれている可能性がある。

そのため、`/etc` やQPKG設定ディレクトリ全体を安易にコンテナへ公開しない。

設定ファイルを直接マウントできない場合は、ホスト側で必要な情報のみを抽出してスナップショットファイルに出力し、コンテナ側で参照する方式も検討する。

ホスト側の補助プログラムが必要な場合は、読み取り専用であること、QTSの再起動・アップデート後も動作すること、アンインストールできることを条件とする。

実装前に、採用方式と必要な権限を説明すること。

## 6. Tailnet内での公開

### 6.1 基本方針

Web画面はTailnet内からのみ利用可能とする。

QNAP では Tailscale を動かさない。server-a に QSV 専用 Tailscale ノードと Caddy をコンテナで配置し、QNAP 上の QSV へ LAN 経由で転送する。既存のプロキシ製品・実行形態・証明書の運用を確認し、それに合わせる。

既存 nas-a-admin の方式を踏襲し、QSV 専用ノードを1つ登録する。Caddy はそのネットワークと socket を共有し、専用ホスト名の443で受ける。ホスト自身の Tailscale の8443は使用しない。

### 6.2 ネットワーク要件

- インターネットへの一般公開は行わない
- QSV 専用ノードに既存 tag:www-server を付与し、管理者と tag:client の TCP 443 を既存 grants で許可する
- server-a のリバースプロキシで Tailnet 向け入口を提供する
- QNAP のバックエンドは指定 LAN IP・専用ポートを使い、server-a の実際の送信元のみ許可する
- QSV_ALLOWED_PROXY_IPS で中継するプロキシの実接続元 IP を指定し、アプリ層で許可外の要求を HTTP 403 とする
- 空の allowlist は全拒否、不正な IP は起動エラーとする。転送ヘッダーを IP 判定に使わない
- Docker のポート公開経路でも接続元を区別でき、IP 制限が有効であることを実機で確認する
- HTTPS終端は既存構成と整合させる
- NASの管理画面などとポートが衝突しないこと

ブラウザ向け HTTPS は server-a で終端する。QNAP との間は信頼するホーム LAN 経由の HTTP とし、プロキシの送信元 IP 制限だけを採用する。この区間は Tailscale による暗号化の対象外であることを前提とする。バックエンドの追加認証情報・パスワード・トークンは不要とする。

Tailnet内であることを理由に、Webアプリケーションをあらゆるネットワークインターフェースに無条件で公開しない。

### 6.3 認証

server-a の入口には既存の Tailnet アクセス制御を適用する。これは QNAP の LAN ポートへの直接接続を制限しないため、バックエンドの送信元制限を別途必須とする。

リバースプロキシ側には独自の IP allowlist を追加せず、Tailscale ACL でアクセス制御する。QSV の allowlist は中継するプロキシの IP だけを対象とし、Tailnet クライアント IP は登録しない。

アプリケーション独自のユーザー管理・パスワード・トークン認証は実装しない。

ただし、アクセス制御の成立条件と、Tailnet外からアクセスできないことの検証方法をドキュメント化する。

## 7. データ更新

### 7.1 収集間隔

- 起動時に初回収集
- 以降、一定間隔で自動更新
- 初期設定では5分ごとの更新
- UIから手動再取得が可能
- 最終更新時刻を表示

NAS設定が頻繁に変更されることは想定しないため、リアルタイム監視は不要とする。

### 7.2 キャッシュ

- 収集結果をメモリ内またはローカルキャッシュに保持
- 一時的な収集失敗でも画面自体は利用可能
- 古い情報を表示する場合は明示
- Collectorごとの最終正常取得日時を保持

初期実装では大規模DBは不要。

永続化が必要な場合はSQLiteなどの軽量な仕組みを検討する。

### 7.3 負荷

- QTSに負荷をかけない
- 設定ファイルの頻繁なスキャンを避ける
- 不要な再帰的ファイル探索を行わない
- 収集処理にタイムアウトを設ける
- 特定Collectorのエラーで全体を停止させない

---

## 8. セキュリティ要件

- 完全読み取り専用
- コンテナの非root実行を原則とする
- Linux capabilitiesは最小限にする
- 可能ならコンテナのroot filesystemを読み取り専用にする
- 取得元のパスをHTTPリクエストから自由に指定できない設計にする
- 任意コマンド実行APIを実装しない
- スケジュール表示のためにジョブのコマンドを実行しない
- 設定ファイル中の文字列をHTMLとして解釈・実行しない
- 機密情報を含む生データをブラウザへ送信しない
- ログにパスワードやトークンを出力しない
- 外部CDNや外部APIに依存せず動作できることが望ましい

収集用に必要な権限が大きい場合は、Web公開プロセスと収集処理の権限分離を検討する。

---

## 9. 非機能要件

### 9.1 操作性

- 日本語UI
- PC・スマートフォン両対応
- ダークモード対応
- 画面更新時に状態が不自然にリセットされない
- 一般的なNAS管理者が理解できる表記を使用

### 9.2 リソース

- 低CPU負荷
- 低メモリ使用量
- 常時稼働前提
- NAS再起動後に自動起動
- ネットワーク接続がなくてもローカルで正常動作

### 9.3 保守性

- Collectorの追加が容易
- QTSのバージョン差に対応しやすい
- ソースコードに適切な型定義を設ける
- 収集処理の単体テストを用意
- 実機依存部分はテスト用データで再現できるようにする

---

## 10. 開発の進め方

### Phase 1：QTS実機調査

最初に以下を確認する。

1. QTSのバージョンとCPUアーキテクチャ
2. Container Stationのバージョン
3. `/etc/config/crontab` の内容と書式
4. 電源スケジュールの保存方式

## 13. 実装にあたって特に重視すること

### 13.1 網羅性と正確性

本プロジェクトの最大の目的は、**QTSの各所に分散しているタイマー設定をまとめて確認できること**である。

cronのWeb UIを作るだけでは目的を達成できない。

一方で、取得不可能な情報を推測して表示することも避ける。

取得可能な情報はできるだけ網羅し、取得できない部分についてはその事実を明示すること。

### 13.2 不要な機能を増やさない

本ツールには設定変更機能は不要である。

認証・ユーザー管理・通知・ジョブ実行・設定編集なども、当面は実装しない。

あくまでスケジュールの「見える化」に特化する。

### 13.3 実機への影響を最小限にする

QTSはNASの基盤OSであり、内部設定にアクセスするために動作を変更することは望ましくない。

読み取り専用で実現できない場合は、無理に実装せず、制約と代替方式を提示すること。

### 13.4 調査結果を先に確定する

QTSの内部ファイル形式やAPIを推測だけで実装しない。

特に、電源スケジュール、スナップショット、HBS 3、RAID関連については、取得方式を実機で確認すること。

安全性に関わる実装判断については、根拠を示したうえで実装を進める。

## 15. 最終的な期待

QNAPの管理画面で個別に確認しているスケジュールを、このWebアプリケーションを開くだけで横断的に把握できること。

特に、**「毎週何曜日の何時に、NASのどの機能が動く予定なのか」** がひと目で分かる画面を実現してほしい。

設定変更は従来どおりQTS標準の管理画面で実施するため、本ツールは参照と可視化に徹すること。
